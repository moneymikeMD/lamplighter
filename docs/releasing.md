# Releasing lamplighter

A release is three independent pipelines that all start from one `vX.Y.Z` tag on `main`.

| Pipeline | Workflow | Produces |
| --- | --- | --- |
| Tagging | `release-please.yml` | Release PR, `CHANGELOG.md`, tag `vX.Y.Z` and tag `lamplighter--vX.Y.Z` |
| Binaries | `release.yml` (generated by cargo-dist) | GitHub Release with `lampl` archives for aarch64-apple-darwin, x86_64-unknown-linux-gnu and aarch64-unknown-linux-gnu, plus `lampl-installer.sh` |
| Crates | `publish.yml` | `lampl-core`, `lampl-embed`, `lampl-store-pg`, `lampl-store-sqlite`, `lampl` and the `lamplighter` name-holder on crates.io |
| Image | `image.yml` | `ghcr.io/moneymikemd/lamplighter:{X.Y.Z,X.Y,latest}`, linux/amd64 and linux/arm64 |

## How a release happens

1. Merge conventional commits (`feat:`, `fix:`, `chore:`) to `main`. release-please keeps one release PR open, bumping the workspace version, the internal path-dependency versions and `Cargo.lock`.
2. Merge the release PR. release-please pushes `vX.Y.Z` using the `moneymike-release` GitHub App token (secrets `RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`). A tag pushed with the default `GITHUB_TOKEN` would not trigger the other workflows.
3. The same job then creates `lamplighter--vX.Y.Z` at the same commit. It runs before the `Cargo.lock` sync step, so a failure there cannot skip it. Plugin dependency ranges in moneymike-plugins resolve only against `<plugin>--v<version>` tags. Neither workflow triggers on that tag: they match `v[0-9]+.[0-9]+.[0-9]+*` anchored at the start.
4. `release.yml`, `publish.yml` and `image.yml` run on the `vX.Y.Z` tag.

Install paths for users: the shell installer attached to the GitHub Release, `cargo install lampl`, and `docker pull ghcr.io/moneymikemd/lamplighter`. The reference bundle is `deploy/compose.yaml`.

## Adding a path dependency between workspace crates

release-please edits version strings through `extra-files` in `release-please-config.json`. A new `path = ..., version = "..."` dependency needs its own `toml` entry, for example `$.dependencies.lampl-core.version` on the depending crate's `Cargo.toml`, or the version drifts and `cargo publish` fails.

## Recovering a failed release

| Failure | Recovery |
| --- | --- |
| `release.yml` failed after the tag exists | Fix forward on `main`, then re-run the failed jobs from the Actions run. release-please owns the GitHub Release, so do not delete it: if the workflow file itself changed, delete and re-push the tag only after saving the release notes, or upload the archives by hand with `gh release upload vX.Y.Z <files>`. |
| `release.yml` `host` job: `a release with the same tag name already exists` | Seen on v0.1.0. dist tried to create the release release-please had already made. Fixed by `create-release = false` in `dist-workspace.toml`: `host` now runs `gh release upload` and `gh release edit --draft=false` on the existing release, leaving its title and notes alone. |
| `publish.yml` failed part-way | Re-run the workflow, or run it with `workflow_dispatch` and the tag. It skips every crate version already on crates.io and publishes the rest. |
| A crate version is broken on crates.io | Versions cannot be overwritten. `cargo yank --version X.Y.Z <crate>`, fix, and release `X.Y.(Z+1)`. |
| `image.yml` failed | Re-run the failed jobs. The `merge` job only runs when both platform builds pushed a digest. |
| Release PR has no checks | The App token is not in use or has expired. Confirm `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY` and that the app is installed on this repo. |
| `lamplighter--vX.Y.Z` tag missing | Create it at the release commit: `gh api repos/moneymikeMD/lamplighter/git/refs -f ref=refs/tags/lamplighter--vX.Y.Z -f sha=<sha>`. |

## One-time steps

The first image push creates the ghcr package as private. An owner must set its visibility to Public (package settings, Danger Zone); the change cannot be undone. Until then the compose bundle cannot pull the image.

The crates.io token is the `CARGO_REGISTRY_TOKEN` repo secret.

## Regenerating `release.yml`

`dist-workspace.toml` sets `allow-dirty = ["ci"]` because `release.yml` is edited after generation: the tag trigger is narrowed to `v[0-9]+.[0-9]+.[0-9]+*` so the `lamplighter--v` tag does not start a second run, and action versions are bumped to current releases. The workflow-level permission is `contents: read`, with `contents: write` only on the `host` job that creates the GitHub Release; dist's generator emits workflow-level `write`, so regenerating would undo this. `create-release = false` makes dist upload to the release release-please created instead of creating one. To upgrade dist or change dist settings, remove `allow-dirty`, run `dist generate`, then repeat these edits and restore `allow-dirty`.

## Follow-ups

`release-please.yml` passes `app-id` to `actions/create-github-app-token`, which that action now deprecates in favour of `client-id`. Switch when the App's client ID is stored as a secret.
